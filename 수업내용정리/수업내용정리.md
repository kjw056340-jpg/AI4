## 01 · Day1 — 프로그램의 기본 흐름

### 핵심 개념

- **변수와 연산:** `number1 = 100`처럼 값을 이름에 연결하고 `+`, `*`, `%`로 계산합니다.
- **입력과 변환:** `input()`은 문자열을 반환합니다. 숫자 계산에는 `int()` 같은 변환이 필요하며 잘못된 입력은 예외가 될 수 있습니다.
- **조건:** 점수 60 이상이면 합격처럼 기준을 `if/else`로 표현합니다. `>=`는 경계값을 포함합니다.
- **반복:** 횟수가 정해지면 `for`, 조건을 만족할 때까지 반복하면 `while`을 사용합니다. `break`는 현재 반복문을 끝냅니다.
- **중첩 반복:** 구구단에서 바깥 반복은 단, 안쪽 반복은 곱하는 수를 바꿉니다. `range(2, 10)`에는 10이 포함되지 않습니다.

![입력부터 조건 분기까지](assets/02-flow.png)

### 대표 실습: 숫자 다섯 개 중 짝수 찾기

원본 `Day1/day1-3.py`의 흐름을 간결하게 정리한 예제입니다.

```python
scores = []
for i in range(5):
    scores.append(int(input(f"{i + 1}번째 숫자: ")))

for score in scores:
    if score % 2 == 0:
        print(score)
```

`% 2`의 결과가 0이면 짝수입니다. 입력과 필터링을 나누면 각 단계의 역할을 확인하기 쉽습니다. 이 예제는 숫자가 아닌 입력의 예외 처리를 생략했습니다. 그 내용은 Day3에서 연결합니다.

### 숫자 맞추기에서 볼 점

`random.randint(1, 100)`은 양 끝을 포함한 정수를 만듭니다. 정답보다 큰지·작은지 비교하고, 정답이면 반복을 끝냅니다. 시도 횟수는 입력을 받을 때마다 증가시킵니다.

**원본 점검:** `day1-5.py`의 `print("정답입니다! 총 시도횟수는 : {count}")`는 앞에 `f`가 없어 `{count}`가 문자 그대로 출력됩니다. 교정하면 `print(f"정답입니다! 총 시도횟수는 : {count}")`입니다. 같은 파일에 게임 두 버전이 있어 첫 게임이 끝나도 다음 입력이 이어질 수 있습니다.

**직접 해보기:** 59·60·61을 입력하면 각각 합격인가요? `[1, 2, 3, 4, 5]`에서 짝수의 합과 개수를 계산해 보세요.

## 02 · Day2 — 판단 규칙과 데이터 가공

### 조건을 조립하는 법

| 표현 | 뜻 | 수업 예시 |
| --- | --- | --- |
| `A and B` | 두 조건이 모두 참 | 활성 계정이고 인증 완료 |
| `A or B` | 하나 이상이 참 | 관리자 또는 매니저 |
| `not A` | 조건의 반대 | 정지되지 않은 계정 |
| `x in values` | 목록 등에 포함 | 허용된 역할인지 확인 |
| `a if 조건 else b` | 조건에 따라 값 선택 | 합격·불합격 문자열 |

**단락 평가:** `and`는 앞이 거짓이면 뒤를 평가하지 않습니다. `user_profile is not None and user_profile.get("is_verified")`처럼 작성하면 None에 메서드를 호출하는 일을 피할 수 있습니다. 원본 `Day2/오전/day2-2.py`의 `use_profile`은 `user_profile`과 이름이 달라 실행 시 오류가 발생합니다.

### 자료구조를 선택하는 기준

| 자료구조 | 용도 | 주의할 점 |
| --- | --- | --- |
| list | 순서 있는 값들, 추가·수정 | 순회 중 원본을 삭제하면 항목을 건너뛸 수 있음 |
| dict | 이름과 값의 연결 | 없는 키를 `[]`로 읽으면 KeyError |
| tuple | 위치가 정해진 값의 묶음 | 요소 자체를 다시 대입할 수 없음 |
| set | 중복 제거·포함 검사 | 입력 순서를 보장하는 용도로 쓰지 않음 |

`dict(zip(["a", "b"], [100, 200]))`은 `{"a": 100, "b": 200}`을 만듭니다. 일반적인 `zip`은 가장 짧은 입력 길이에서 끝납니다.

### 대표 실습: 역할별 권한과 목록 필터

```python
for user in test_users:
    if user["is_suspended"]:
        print("정지된 계정입니다")
        continue
    role = user["user_role"]
    if role in ["admin", "manager"]:
        print("관리 기능 허용")
    elif role == "user":
        print("개인 데이터 조회")
    else:
        print("별도 정책 확인")

items = ["정상", "불량", "불량", "정상"]
clean = [item for item in items if item != "불량"]
```

위 권한 예제는 설명을 위해 원본보다 단순화했습니다. 실제 `day2-7.py`는 admin·manager·user·guest와 알 수 없는 역할을 각각 분리합니다.

`[i for i in numbers if i % 2 == 0]`는 일부 값만 남깁니다. `["성인" if age >= 20 else "미성년" for age in ages]`는 모든 값을 변환하므로 결과 개수가 같습니다.

**금칙어 전처리:** 빈 문자열 제거 → set으로 중복 제거 → 길이 내림차순 정렬 → join으로 연결합니다. 긴 단어부터 확인하는 규칙을 표현한 예입니다. 원본의 `set(1,2,3,...)` 호출은 잘못된 형식이며 `set([1,2,3])`처럼 하나의 iterable을 전달해야 합니다.

**직접 해보기:** `[20,15,60]`을 ‘성인/미성년’으로 바꾸는 결과와 성인만 남기는 결과를 각각 써 보세요. 정지 계정을 역할 검사보다 먼저 처리하는 이유도 설명해 보세요.

## 03 · Day3 — 객체, 예외, 유지보수하기 쉬운 코드

### 객체가 필요한 이유

바리스타 로봇은 원두량과 누적 추출 수를 기억하며 추출 동작을 수행합니다. 서로 다른 로봇 인스턴스는 상태를 따로 가집니다. 디지털 지갑은 잔액과 입금 동작을 묶고 setter로 음수 잔액을 거절합니다.

![데이터와 동작을 묶은 객체](assets/03-object.png)

| 개념 | 수업 속 예 | 기억할 점 |
| --- | --- | --- |
| 생성자 `__init__` | 로봇 이름·원두 초기화 | 인스턴스 상태의 출발점 |
| 인스턴스 메서드 | `brew_espresso()` | `self`의 상태를 읽거나 변경 |
| property | 지갑의 balance | 읽기·쓰기에 규칙을 연결 |
| 상속·오버라이딩 | VisionClassifier, TextSummarizerLLM | 같은 predict 호출에 다른 동작 |
| 추상 클래스 | PaymentGateway | 공통 동작의 구현 의무 표현 |
| dataclass | PaymentReceipt | 필드 중심 데이터의 선언 간소화 |

`__balance`의 이름 맹글링은 실수 방지에 도움이 되지만 보안 경계는 아닙니다. 일반 클래스의 타입 힌트만으로 입력이 자동 검증되지도 않습니다.

**원본 점검:** `Day3/오전/day3-4.py`는 `@abstractmethod`를 사용하지만 `ABC`를 상속하지 않습니다. 추상 메서드의 구현을 강제하려면 다음처럼 작성합니다.

```python
from abc import ABC, abstractmethod

class PaymentGateway(ABC):
    @abstractmethod
    def process_payment(self, item: str, amount: int) -> str:
        pass
```

### 예외는 입력의 실패 원인을 구분하는 도구

로그 문자열을 split하여 dict로 만든 뒤 숫자로 변환하는 실습에서는 숫자 형식이 틀리면 ValueError, 키가 빠지면 KeyError가 발생합니다. 원본 `day3-1.py`는 split 전처리가 try 바깥에 있어 형식이 깨진 로그의 모든 오류를 처리하는 구조는 아닙니다.

- `try`: 실패할 수 있는 처리
- `except`: 해당 예외에 대한 대응
- `else`: try가 정상 종료되었을 때 수행
- `finally`: 예외 발생 여부와 관계없이 정리·기록

**주의:** `except Exception`으로 모든 문제를 같은 메시지로 바꾸면 원인이 감춰질 수 있습니다. 아는 오류를 좁게 처리하고, 원인 정보와 사용자용 설명을 구분하세요.

### 리팩터링 사례 두 가지

**주문 계산:** 등급 숫자를 Enum 이름으로 바꾸고 할인율을 한곳에 모읍니다. 가격·수량·쿠폰을 검증한 후 ‘등급 할인 → 쿠폰 차감 → 최소 0원 → 원 단위 버림’ 순서를 유지합니다. 수정본은 금액 계산에 정수 연산을 사용합니다. Python에서 bool은 int의 하위 타입이므로 bool 허용 여부도 별도로 판단합니다.

**점수 전처리:** 원본 `day3-4.py`는 키 누락·변환 실패·범위 초과를 방어하지 못합니다. `fixed`와 `after` 버전은 구조·키·bool·변환·유한수·0~100 범위를 검사합니다. 유효한 점수만 100으로 나누고, after 버전은 행별 오류와 성공률 등을 보고서로 만듭니다. 빈 입력의 평균이나 성공률은 계산 불가를 나타내는 None으로 처리합니다.

**직접 해보기:** `{"score": "N/A"}`, `{"score": 120}`, `{"score": True}`, `{}`를 왜 각각 거절해야 할까요? 잘못된 행을 건너뛰면 입력과 결과의 길이가 같을까요?

## 04 · Day4 — 값의 교환과 대입 순서

확인한 `Day4/day4-1`은 확장자 없는 Python 코드이며 난수 열 개를 만든 뒤 양끝 인덱스에 대입합니다.

```python
# 원본: 첫 값을 덮어쓴 뒤 같은 값을 다시 읽습니다.
numbers[0] = numbers[-1]
numbers[-1] = numbers[0]

# 교정 예제: 오른쪽 두 값을 먼저 평가하여 교환합니다.
numbers[0], numbers[-1] = numbers[-1], numbers[0]
```

| 단계 | 원본: [10,20,30] | 교정 예제 |
| --- | --- | --- |
| 시작 | [10,20,30] | [10,20,30] |
| 첫 대입 후 | [30,20,30] | 오른쪽에서 30,10을 먼저 준비 |
| 최종 | [30,20,30] | [30,20,10] |

**핵심:** 대입은 이전 값을 자동으로 기억하지 않습니다. `numbers[-1]`은 마지막 요소입니다. 이 예제는 길이 10의 리스트를 만들어 빈 리스트의 인덱스 문제는 발생하지 않습니다.

Uvicorn이 서버를 실행하고 FastAPI가 메서드·경로에 맞는 함수를 찾습니다. 경로·쿼리·본문에서 입력을 받고, 처리 결과는 응답으로 전달됩니다.

| Path | 대상을 식별 | `/tasks/{task_id}` |
| Query | 검색·필터·페이지 조건 | `?q=Python&done=false&skip=0&limit=10` |

## 06 · Day6 — Pydantic으로 데이터 검증

### 모델은 데이터의 규칙을 선언한다

일반 클래스의 `age: int`는 주로 설명과 정적 분석을 위한 힌트입니다. Pydantic의 BaseModel은 인스턴스를 만들거나 model_validate를 호출할 때 실제 데이터를 검사합니다.

```python
from pydantic import BaseModel, ConfigDict, Field

class Product(BaseModel):
    model_config = ConfigDict(extra="forbid")
    title: str = Field(min_length=2, max_length=60)
    price: int = Field(gt=0, strict=True)
    stock: int = Field(default=0, ge=0)
    sku: str = Field(pattern=r"^SKU-[0-9]{4}$")
```

위는 원본 실습의 TODO 조건에 맞춘 **교정 예제**입니다. 원본 `exercise.py`는 ‘가격 0보다 큼’이라는 주석과 달리 `ge=0`이라 0을 허용하고, product·ValidationError·main 정의도 빠져 있어 그대로 실행할 완성본으로 보면 안 됩니다.

![검증 전후의 데이터 흐름](assets/04-validation.png)

| 선언 | 의미 | 예 |
| --- | --- | --- |
| `age: int` | 필수 필드 | 일반 설정에서는 `"34"`를 34로 변환 가능 |
| `nickname: str \| None = None` | 생략·None 허용 | 선택 별명 |
| `value: int \| str` | 여러 타입 허용 | 정수·문자열 학번 |
| `gt=0` / `ge=0` | 0 초과 / 0 이상 | 가격 / 재고 |
| `strict=True` | 자동 변환을 제한 | 엄격한 정수 입력 |
| `extra="forbid"` | 정의하지 않은 필드 거절 | 오타 필드 발견 |
| `model_dump()` | 모델을 dict로 변환 | 출력·후속 처리 |

None을 허용하는 타입과 생략 가능한 필드는 같은 뜻이 아닙니다. `nickname: str | None`만 선언하면 값은 None일 수 있어도 필드는 여전히 필수이며, 생략까지 허용하려면 기본값을 지정해야 합니다.

### 필드·모델·중첩 검증

`field_validator`는 아이디 공백·소문자 정리나 태그 문자열 분해처럼 한 필드에 규칙을 둡니다. `mode="before"`는 타입 검증 이전의 입력을 다룰 수 있습니다. `model_validator(mode="after")`는 비밀번호 확인 일치, 예약 시작·종료일 순서처럼 여러 필드의 관계를 검사합니다.

원본 Reservation의 조건 `start > end`는 **종료일이 시작일보다 이르면 거절**한다는 뜻입니다. 원본 오류 메시지는 이 관계를 반대로 표현하므로 조건식을 기준으로 읽어야 합니다. 시작일과 종료일이 같은 경우는 이 조건에서 허용됩니다.

중첩 모델에서는 Order 안에 Address, `list[OrderItem]`, 배송 방식 Enum을 넣습니다. `ValidationError.errors()`의 loc는 예를 들어 `('items', 0, 'quantity')`처럼 잘못된 위치를 알려 줍니다.

## 07 · Day7 — 기다림을 겹치는 비동기 처리

### async는 어디서 기다리느냐가 중요하다

`async def`만 붙여도 모든 처리가 빨라지지는 않습니다. 이벤트 루프 안에서 `time.sleep(2)`를 직접 호출하면 다른 작업도 기다립니다. `await asyncio.sleep(2)`는 기다리는 동안 다른 작업이 진행될 기회를 줍니다. 기존 동기 I/O 함수를 유지해야 한다면 수업 예제처럼 `await asyncio.to_thread(...)`로 별도 스레드에 맡길 수 있습니다.

![순차 대기와 동시 대기 시간 비교](assets/05-concurrency.png)

이 그림은 각각 2초씩 기다리는 두 작업의 **이론적 비교**이며 이번 작업의 실제 측정 결과가 아닙니다. 실제 시간에는 실행 비용·네트워크·서버 제한 등이 더해집니다. 동시성은 여러 I/O 대기를 겹치는 개념이며 CPU 계산의 병렬 실행을 자동 보장하지 않습니다.

```python
import asyncio

async def make_drink(name):
    await asyncio.sleep(2)
    return name

async def main():
    drinks = await asyncio.gather(
        make_drink("커피"), make_drink("차")
    )
    print(drinks)

asyncio.run(main())
```

### 외부 API를 읽을 때의 확인 순서

1. 연결과 타임아웃을 확인합니다.
2. `response.raise_for_status()`로 실패 HTTP 상태를 확인합니다.
3. JSON 변환이 가능한지 확인합니다.
4. dict·필수 키·필드 타입 등 업무에 필요한 응답 구조를 검증합니다.
5. 요청 ID와 응답을 함께 보관해 완료 순서가 바뀌어도 연결을 유지합니다.

**원본에서 찾은 점검 포인트**

- `Day7/02/main.py`의 `'f/todos/{todo_id}'`는 f-string이 아닙니다. 의도한 주소는 `f'/todos/{todo_id}'`입니다. `raise_for_status()`가 빠져 HTTPStatusError 처리도 기대대로 작동하지 않으며 실패 후 data가 정의되지 않는 경로도 주의해야 합니다.
- `Day7/03/main.py`는 as_completed로 완료된 순서대로 결과를 모은 뒤 원래 ID와 zip합니다. 응답이 2→3→1 순서로 끝나면 요청 ID가 잘못 연결될 수 있습니다. 작업이 `(item_id, data)`를 함께 반환하도록 바꾸면 관계를 보존할 수 있습니다.
- gather는 결과를 전달한 작업의 순서로 모으며, as_completed는 완료 순서로 처리합니다. 실패 전파·취소 정책은 별도로 설계해야 합니다.
- mock_api.py는 지연·404·503·깨진 JSON·필드 누락·429·재시도를 실험할 자료입니다. 파일에 시나리오가 있다고 해서 모든 방어 로직이 구현되어 있다는 뜻은 아닙니다.

### 실패 응답 뒤에도 상태가 맞아야 한다

![예약의 성공·실패·회복 시나리오](assets/06-reservation.png)

정원 4석에서 3석 예약 성공 → 2석 추가 예약 거절 → 1석 예약 성공이 되어야 합니다. 기대 상태는 201 → 409 → 201이며 잔여 좌석은 1 → 1 → 0입니다. 거절 전에 좌석을 빼면 실패가 다음 요청까지 망가뜨립니다. `raise HTTPException`은 앞서 변경한 메모리 상태를 자동으로 되돌리지 않습니다.

```python
# 교정 원리: 먼저 확인하고 성공할 때만 변경합니다.
if body.seats > app.state.remaining:
    raise HTTPException(status_code=409, detail="Not enough seats")
app.state.remaining -= body.seats
```

이 간단한 메모리 예제는 단일 프로세스 학습용입니다. 운영 환경의 동시 예약·여러 worker·영속성까지 보장하는 구현으로 확대 해석하지 않습니다.

### CRUD는 요청 하나보다 데이터의 이어지는 변화가 중요하다

| 작업 | 수업의 HTTP 예 | 확인할 계약 |
| --- | --- | --- |
| Create 생성 | POST /tasks | 새 ID 발급과 201 |
| Read 조회 | GET /tasks, GET /tasks/{task_id} | 저장 데이터 조회, 없는 대상 404 |
| Update 교체 | PUT /tasks/1 | 이 수업에서는 제목·완료 상태를 함께 전달 |
| Update 부분 수정 | PATCH /tasks/1 | 보내지 않은 필드는 보존 |
| Delete 삭제 | DELETE /tasks/{task_id} | ID가 일치하는 데이터 삭제, 성공 204 |

**ID와 위치는 다릅니다.** ID가 1·3인 목록의 길이는 2이므로 `len(tasks)+1`은 이미 존재하는 ID 3을 만듭니다. 또한 `tasks.pop(task_id)`는 ID를 찾는 것이 아니라 그 번호의 인덱스를 삭제합니다.

학습용 ID 생성은 `max((task["id"] for task in tasks), default=0) + 1`처럼 현재 ID에서 계산할 수 있습니다. 운영 환경의 동시 생성까지 안전하게 보장하는 방식은 아니며, DB 기본키 발급과는 구분합니다. 원본 lesson_04의 생성 함수는 빈 목록에서 `max()`를 호출하므로 전체 삭제 뒤 다시 등록하는 경우도 점검할 만합니다.

### PATCH에서 생략과 값 전달을 구분하기

# 설명용 교정: 요청에 실제 포함된 필드만 반영합니다.
changes = payload.model_dump(exclude_unset=True)

## 10 · Day10 — SQL, 트랜잭션, 관계형 데이터

**자료:** `Day10/lesson_01 ~ lesson_08`의 README·main·solution·check. 주로 Python 표준 sqlite3를 사용하는 독립 실습입니다. 각 파일이 사용하는 `autocommit` 매개변수는 Python 3.12 이상에서 제공되므로 오래된 환경에서는 같은 코드가 실행되지 않을 수 있습니다.

### 메모리에서 파일로: 조회됐다고 저장이 확정된 것은 아니다

메모리 목록은 프로세스가 끝나면 사라집니다. SQLite는 파일에 데이터를 보관하지만, 수업의 트랜잭션 설정에서는 INSERT 뒤 commit해야 변경을 확정합니다. 같은 연결에서 조회된 행이 재연결 뒤에도 남는지 확인해야 합니다.

| SQL | 의미 | 함께 확인할 점 |
| --- | --- | --- |
| INSERT | 행 추가 | 매개변수 바인딩·commit |
| SELECT | 행 조회 | WHERE·ORDER BY·LIMIT |
| UPDATE | 행 수정 | WHERE와 변경된 행 수 |
| DELETE | 행 삭제 | ID 조건·없는 대상 정책 |
| JOIN | 관련 테이블 연결 | 연결 기준과 누락 행 |
| GROUP BY | 묶어서 집계 | COUNT의 대상과 NULL |

```sql
-- 설명용 조회: 도시 필터 → 점수순 → 동점은 ID순 → 개수 제한
SELECT id, nickname, points
FROM users
WHERE city = ?
ORDER BY points DESC, id ASC
LIMIT ?;
```

SQLite에서 `?`에 값을 바인딩하면 `O'Neil` 같은 따옴표 포함 값도 SQL 문법과 분리해 전달할 수 있습니다. PostgreSQL psycopg 예제의 자리표시자는 `%s`이므로 그대로 섞어 쓰지 않습니다. 값 바인딩은 테이블명 같은 SQL 식별자를 넣는 용도와도 다릅니다.

### 트랜잭션: 함께 성공하거나 함께 취소하기

질문 저장과 답변 저장을 한 묶음으로 취급한다면 두 INSERT 뒤에 commit하고, 중간 실패에는 rollback해야 합니다. 첫 작업 직후 commit하면 두 번째가 실패해도 이미 확정된 첫 변경은 나중의 rollback으로 돌아오지 않습니다.

**Day8과 연결:** 메모리 값을 바꾼 뒤 HTTPException을 일으키면 자동 복구되지 않았습니다. DB에서도 트랜잭션 범위와 확정 시점을 직접 맞춰야 실패 후 상태를 보존할 수 있습니다.

### 사용자 → 대화방 → 메시지 관계

**users 1 → N conversations 1 → N messages**

한 사용자는 여러 방을 만들고, 한 방에는 여러 메시지가 쌓입니다. 기본키는 행을 식별하고 외래키는 부모 행과 연결합니다. conversations.user_id에 UNIQUE를 걸면 한 사용자당 방 하나로 제한되어 수업의 1:N 요구와 충돌합니다.

| 차시 | 결함·질문 | 교정·검증 방향 |
| --- | --- | --- |
| 1 저장 확정 | INSERT 뒤 commit 누락 | 연결을 닫고 다시 읽어 저장 확인 |
| 2 조회 조건 | `limit or 2`가 0을 2로 바꿈 | 0을 의미 있는 입력으로 보존, 동점 정렬도 검사 |
| 3 수정·삭제 | 두 작업 사이 commit | 한 트랜잭션으로 묶고 실패 시 전체 보존 확인 |
| 4 제약조건 | CHECK만으로 NULL 점수를 막지 못함 | 필수값은 NOT NULL도 지정 |
| 5 ERD | user_id의 UNIQUE가 다중 방 생성 차단 | 관계 요구에 맞게 제약 수정 |
| 6 외래키 | 트랜잭션 안에서 활성화해 적용되지 않음 | 트랜잭션 시작 전 켜고 PRAGMA 결과 확인 |
| 7 LEFT JOIN | 메시지 없는 방도 COUNT(*)가 1 | 실제 메시지 키인 COUNT(m.id)로 집계 |
| 8 이력 모듈 | 저장은 소유자 확인, 조회는 방 ID만 확인 | 조회에도 사용자 ID 조건 추가 |

차시 6의 현재 main은 autocommit=False 연결에서 PRAGMA를 실행합니다. solution처럼 설정을 적용할 수 있는 시점에 활성화하고 실제 값을 확인하는 것이 중요합니다. 이 문서의 표는 소스 분석이며 새 실행 결과가 아닙니다.

### 읽기에도 소유권 검사가 필요하다

```sql
-- 설명용 교정: 요청자가 소유한 방의 메시지만 조회
SELECT m.id, m.role, m.content
FROM messages AS m
JOIN conversations AS c ON c.id = m.conversation_id
WHERE c.id = ? AND c.user_id = ?
ORDER BY m.id;
```

원본 lesson_08의 list_history는 user_id 인자를 받지만 SQL에서 사용하지 않습니다. 함수에 인자를 받았다는 사실만으로 접근 제어가 생기지 않습니다. 쓰기와 읽기에 같은 소유권 정책이 적용되는지 모두 검사해야 합니다.

**별도 결과물:** `Day10/demo`는 회원·게시판·댓글·마스킹 화면의 목업입니다. README에 따르면 계정과 게시글 상태는 브라우저 저장소 기반이며, 실제 DB 회원 인증이나 실제 비밀번호 찾기 메일 전송과는 구분해야 합니다. 해당 프로젝트의 버전 추천·배포 기록을 이번 수업 정리에서 새 검증 결과로 인용하지 않았습니다.

## 11 · Day11 — PostgreSQL 연결과 로컬 AI 대화

### 같은 SQL 개념을 다른 저장소로 옮기기

`Day11/main.py`는 파일 위치 기준 config.json을 읽어 psycopg로 Supabase PostgreSQL에 연결하고 `current_database()`와 `current_user`를 조회합니다. **DB에 연결됐는지 확인하는 실습**이지 웹 로그인 API는 아닙니다. 실제 host·user·password·프로젝트 키 등 연결값은 이 정리에 복사하지 않았습니다.

`main2.py`는 ch2 스키마에 users를 준비한 뒤 다음을 수행합니다.

**테이블 준비 → 여러 사용자 INSERT → 전체 SELECT → 이메일 조건 UPDATE → 이메일 조건 DELETE → 재조회**

- `GENERATED ALWAYS AS IDENTITY`로 ID를 발급하고 PK로 식별합니다.
- name·email에는 NOT NULL, email에는 UNIQUE가 있습니다.
- `executemany()`는 여러 입력에 같은 SQL을 적용합니다.
- psycopg의 `%s`와 별도 튜플로 값을 전달합니다.
- 해당 코드의 `with psycopg.connect(...)`는 정상 종료 시 commit, 예외 시 rollback하고 연결도 닫는 수명을 제공합니다. sqlite3 연결의 with와 동일하다고 가정하지 마세요.

**원본 점검:** main2.py는 시작할 때 `DROP TABLE IF EXISTS ch2.users`를 실행하므로 재실행 시 기존 실습 데이터를 지우는 구조입니다. 분석만 수행했으며 실제 DB에 연결하거나 실행하지 않았습니다.

**Swagger/브라우저 → APIRouter → UserCreate 검증 → psycopg 연결 → PostgreSQL SQL → dict 행 → JSON**

| 요소 | 현재 main.py의 동작 |

## 13 · Day13 — 로그인, 토큰 검증, 내 메모 접근 제어

**자료:** `Day13/main.py`, `main2.py`, `main3.py`. 파일 안의 ‘차시’ 표시는 Day13 내부 실습 구분이며 날짜 Day 번호가 아닙니다.

| 파일 | 구현 범위 |
| --- | --- |
| main.py | POST /auth/login, POST /auth/signup |
| main2.py | 로그인 + Bearer 토큰으로 GET /me |
| main3.py | 로그인·현재 사용자 의존성 + SQLite 메모 생성·목록·개별 조회 |

### 1. 가입과 로그인은 다르다

가입은 `auth.sign_up`, 로그인은 `auth.sign_in_with_password`를 호출합니다. 로그인 모델은 EmailStr로 이메일 형식을 검사하고 비밀번호는 SecretStr로 받습니다. 로그인은 기존 비밀번호를 확인하는 일이므로 비밀번호 앞뒤 공백을 제거하거나 가입용 강도 규칙을 다시 적용하지 않습니다.

main.py의 가입 모델에는 길이 8~128의 규칙이 있습니다. 가입 응답은 안내 문구이며 이메일 확인 설정에 따라 다음 절차가 달라질 수 있습니다. 가입 안내를 받았다는 것과 즉시 로그인 가능한 세션을 받았다는 것은 구분해야 합니다.

### 2. 토큰의 역할을 구분하기

| 값 | 용도 | 혼동하지 말 것 |
| --- | --- | --- |
| 프로젝트 publishable 키 | 어떤 Supabase 프로젝트에 요청할지 연결 | 사용자 본인을 입증하는 access token과 다름 |
| access_token | 보호 API에 제시하는 사용자 JWT | 내용을 읽는 것과 진위 검증은 다름 |
| refresh_token | 새 세션 토큰을 받는 데 사용 | JWT 형태라고 가정하지 않음 |
| expires_in / expires_at | 발급 기준 기간 / 절대 만료 시각 | 서로 다른 시간 표현 |
| SecretStr | 모델 표시에서 비밀 문자열을 가림 | 암호화·해싱·자동 로그 보안이 아님 |

원본은 token 응답에 `Cache-Control: no-store`를 지정하고 422 오류에서 원본 input을 제외합니다. SDK 전체 응답 대신 API에 필요한 필드만 반환합니다. refresh_token을 응답한다고 해서 이 세 파일에 토큰 갱신 경로까지 구현되어 있는 것은 아닙니다.

### 3. HTTPBearer는 추출, get_user는 검증

```text
Authorization: Bearer <access_token>
    ↓ HTTPBearer: 헤더에서 토큰 추출
    ↓ get_current_user: 공통 의존성
    ↓ Supabase auth.get_user(token): 사용자 확인
    ↓ CurrentUser(id, email)
    ↓ 보호된 경로 실행
```

HTTPBearer는 헤더를 읽고 Swagger의 인증 입력을 연결하지만 JWT 서명·만료를 혼자 검증하지 않습니다. 현재 소스는 Auth 서버의 get_user로 사용자를 확인합니다. `Depends(get_current_user)`처럼 함수를 전달하면 FastAPI가 요청 처리 중 의존성을 실행합니다. `get_current_user()`를 등록 시점에 미리 호출하는 것과 다릅니다.

로그인 후 여러 요청에서 재사용하는 공통 사용자 확인 절차를 의존성으로 분리하면 메모 생성·조회마다 같은 인증 규칙을 적용하기 쉽습니다. 사용자별 전역 SDK 세션에 의존하지 않도록 요청용 클라이언트의 세션 저장·자동 갱신 설정도 명시되어 있습니다.

### 4. 인증과 인가: 로그인했다고 모든 메모를 읽지는 못한다

main3.py의 메모 저장소는 PostgreSQL이 아닌 **NOTES_DB로 지정한 SQLite 파일**입니다. 각 메모에는 id, owner_id, content가 있습니다.

| 경로 | 핵심 규칙 |
| --- | --- |
| POST /notes | content를 검증하고 owner_id는 확인된 user.id로 서버가 결정 |
| GET /notes | `WHERE owner_id = ?`로 내 메모만 조회 |
| GET /notes/{note_id} | `WHERE id = ? AND owner_id = ?`로 ID와 소유자 모두 확인 |

```python
# main3.py의 접근 제어 핵심
row = db.execute(
    "SELECT id, owner_id, content FROM notes "
    "WHERE id = ? AND owner_id = ?",
    (note_id, user.id),
).fetchone()
if row is None:
    raise HTTPException(404, "메모를 찾을 수 없습니다.")
```

요청 본문에 owner_id를 받아 신뢰하지 않습니다. 없는 ID와 타인 소유 ID는 같은 404로 응답해 둘을 구분하지 않는 정책입니다. UUID 메모 ID의 정렬은 생성 시간순을 뜻하지 않으므로 현재 `ORDER BY id`를 최신순 조회로 설명하지 않았습니다.

DB 의존성은 yield로 연결을 전달하고 finally에서 닫습니다. 쓰기 뒤 commit이 있으며, `check_same_thread=False`는 스레드 검사 제한을 푸는 설정입니다. 여러 쓰기를 자동으로 안전하게 만드는 장치는 아닙니다.

### 5. 무엇을 테스트해야 하나요?

| 시나리오 | 현재 코드의 정책상 확인할 결과 |
| --- | --- |
| 형식이 잘못된 이메일·빈 비밀번호·추가 필드 | 422, 오류 원문에 비밀번호가 되돌아오지 않음 |
| 잘못된 로그인 정보 | 해당 Auth 오류를 401로 분류 |
| 이메일 미확인 | 해당 Auth 오류를 403으로 분류 |
| 요청 과다·Auth 통신 실패 | 각각 429·503 처리 |
| Bearer 누락·유효하지 않은 사용자 토큰 | 보호 경로 거절, 401 분류 확인 |
| A가 메모 생성 | owner_id가 본문 값이 아니라 검증된 A의 ID |
| B가 A의 메모 목록·개별 조회 시도 | 목록에서 제외, 개별 조회 404 |
| 공백뿐인 메모·2000자 초과 | 입력 검증 실패 |

이 표는 소스에서 도출한 **검증 계획**입니다. 실제 계정 가입, 로그인, 메모 생성이나 외부 DB 변경은 이번 문서 정리에서 수행하지 않았습니다. main.py에는 같은 RequestValidationError 처리기가 두 번 등록되어 후자의 등록이 사용되는 중복도 있으며, 현재 두 함수의 취지는 동일합니다.

**직접 해보기:** A의 유효한 토큰으로 B의 note_id를 요청하면 왜 200이 아니어야 할까요? HTTPBearer와 auth.get_user가 각각 맡는 일을 구분해 보세요.
