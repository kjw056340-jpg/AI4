# 1단계: 요구사항, 화면 및 API 확정

이 프로젝트는 FastAPI 한 서버가 HTML 템플릿, 정적 파일, JSON API를 모두 제공합니다. 프론트엔드는 Vanilla JavaScript의 fetch로 같은 출처의 `/api`와 통신합니다. 데이터는 Supabase PostgreSQL에만 저장하며, 백엔드에서 HTTP Data API를 호출합니다. React, Vue, Node.js, npm, webpack은 사용하지 않습니다.

## 가정과 범위

- 서비스명은 `온도(ondo)`, 생활용품 편집숍입니다.
- KRW 정수 금액, 무료배송, 상품 옵션·쿠폰·세금 별도 계산 없음.
- 상품 등록/수정·재고·판매 여부 변경과 전체 주문 조회는 관리자 전용 `/admin` 화면에서 수행합니다. 관리자 역할 지정은 신뢰된 운영자가 SQL Editor에서 수행합니다.
- 상품은 삭제 대신 `is_active=false`로 판매 중지합니다. 주문의 상품 FK를 보존합니다.
- 회원가입·이메일 확인은 Supabase Auth 설정을 따릅니다. 비밀번호 분실 복구·SNS 로그인 화면은 이번 범위에 없습니다.
- 이메일 확인이 필요하면 안내 후 로그인 화면으로 이동하며, 확인을 끈 테스트 환경에서는 가입 직후 로그인합니다. 비밀번호는 문자와 숫자를 포함한 10자 이상, UTF-8 72바이트 이하입니다.
- 사용자당 장바구니 하나, 최대 50종, 상품별 최대 99개입니다.
- 재고는 주문 확정 시 확인하고 결제 성공 시 다시 확인한 후 차감합니다. 결제 대기 주문은 재고를 예약하지 않습니다.
- 주문 확정 시 가격이 바뀌었으면 최신 가격으로 주문을 생성하고, 결제 직전 화면에서 최종 금액을 다시 보여줍니다. 확정 이후에는 저장한 가격을 유지합니다.
- 모의 결제만 지원하며 카드번호를 입력하거나 외부 PG로 전송하지 않습니다. 성공한 결제 이력을 저장합니다. PG 실패·환불·배송 추적은 범위 밖입니다.
- 결제 전 주문은 취소할 수 있습니다. 결제 완료 주문의 취소/환불은 제공하지 않습니다.
- 탈퇴는 계정 비활성화와 개인정보 익명화로 구현합니다. 이메일·비밀번호 해시·이름·전화번호·주소와 주문 배송정보를 지우고 UUID 및 주문·결제 기록을 남깁니다. 결제 대기/장바구니 상태는 취소합니다.
- 실제 판매에 사용할 개인정보 보존 기간과 탈퇴 정책은 운영 목적에 맞게 별도로 정해야 합니다.

## 화면 목록

| 경로 | 화면 | 로그인 | 동작 |
| --- | --- | --- | --- |
| `/` | 홈 | 불필요 | `/products`로 이동 |
| `/products` | 상품 목록 | 불필요 | 카테고리, 페이지 이동, 상세 |
| `/product?id=UUID` | 상품 상세 | 불필요 | 수량 선택, 장바구니, 바로 구매 |
| `/login?next=...` | 로그인 | 불필요 | 로그인 성공 후 허용된 직전 경로로 복귀 |
| `/register?next=...` | 회원가입 | 불필요 | 이메일 확인 안내 또는 자동 로그인 후 복귀 |
| `/cart` | 장바구니 | 필요 | 수량 변경·삭제, 배송정보 입력으로 이동 |
| `/checkout?source=cart` | 장바구니 주문 | 필요 | 배송정보 입력 → 주문 확정 |
| `/checkout?source=direct&product_id=UUID&quantity=1` | 바로 구매 | 필요 | 기존 장바구니를 보존하며 별도 주문 생성 |
| `/checkout?order_id=UUID` | 결제 | 필요 | 확정 금액 확인·모의 결제 → 상품목록 |
| `/account` | 회원정보 | 필요 | 수정, 비밀번호 변경, 탈퇴, 구매내역 연결 |
| `/orders` | 구매내역 | 필요 | 결제 완료·대기·취소 내역, 결제 이어하기 |
| `/admin` | 관리자 | 관리자만 | 상품 등록·수정·판매 여부·재고 및 전체 주문 조회 |

## 인증 및 복귀 설계

Supabase Auth의 access/refresh token을 HttpOnly, SameSite=Lax, 운영 시 Secure 쿠키로 보관합니다. 서버가 Auth의 사용자 조회 API로 인증합니다. 보조 서명 쿠키는 토큰과 DB의 `token_version`을 묶어 로그아웃 후 기존 쿠키의 재사용을 차단합니다. 비밀번호 변경은 Auth를 통해 처리하고 다른 기기의 쇼핑몰 세션을 무효화하며 현재 기기에 새 쿠키를 발급합니다.

서버는 보호된 HTML 화면에 인증 없이 접근하면 query string을 포함한 원래 주소를 `next`에 담아 로그인으로 보냅니다. 공개 상세 화면의 바로 구매 버튼은 상품번호와 수량이 있는 checkout 주소를 next로 저장합니다. API의 401도 현재 화면을 next로 보냅니다. 로그인 API는 같은 사이트의 지정 화면 경로만 허용하여 외부 사이트로의 open redirect를 막습니다. 가입 화면도 next를 전달받습니다. 장바구니 담기는 로그인 후 상세 화면으로 돌아오며 버튼을 다시 누르면 됩니다.

## 보안 경계

Supabase `auth.users`가 인증을 담당하고 `public.users.auth_user_id`로 쇼핑몰 프로필에 연결합니다. 서버 전용 secret/service_role 키만 사용하며 모든 쇼핑몰 테이블 RLS 활성화, anon/authenticated 접근권한 및 RPC 실행권한을 제거합니다. 별도의 직접 접근 RLS 정책이 없는 것은 의도된 구조입니다. 모든 공개/개인 데이터 접근은 FastAPI를 통과합니다. 관리자 역할은 수정 가능한 Auth metadata가 아닌 서버 전용 `users.role`에서 확인합니다.

서버는 Supabase Auth로 인증하고 세션 버전을 검증한 회원만 DB의 `p_user`로 전달합니다. 주문·결제 조회는 항상 user_id로 필터링하고, 쓰기는 DB 함수 안에서도 주문 소유자와 token_version을 확인합니다. 클라이언트가 보낸 user_id·금액·결제상태는 받지 않습니다.

쓰기 API 전체에 Origin 확인, SameSite 쿠키, double-submit CSRF 쿠키와 `X-CSRF-Token` 헤더를 적용합니다. CSP와 출력 이스케이프, 입력 검증을 함께 적용합니다. 동적 문자열은 HTML에 삽입 전 이스케이프하고, 이미지 경로는 고정된 키 목록에서 선택합니다. SQL은 고정 쿼리/PLpgSQL 변수로 실행하며 동적 SQL 문자열을 만들지 않습니다. Supabase HTTP 필터는 URL query parameter로 인코딩합니다.

로그인/회원가입은 연결 IP당 1분 15회 제한입니다. 기본 실행은 worker 1개입니다. 프록시 전달 헤더를 임의 신뢰하지 않으므로 Render에서는 여러 사용자가 프록시 주소 하나로 묶일 수 있습니다. 다중 worker/고트래픽 서비스로 확대할 때 신뢰할 프록시 설정과 공유 저장소 기반 제한기로 교체해야 합니다.

## 반응형 설계

viewport meta, 모바일 기본 2열 상품 그리드, 600px·1000px media query, flex/grid와 `minmax(0,1fr)`를 사용합니다. 모바일은 상세·결제·회원정보가 한 열이며, 태블릿/PC에서는 두 열과 요약 사이드바로 바뀝니다. 키보드 포커스, label, 오류 알림, 본문 건너뛰기 링크, reduced-motion도 제공합니다.
